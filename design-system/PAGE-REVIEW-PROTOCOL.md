## Rancana's next pilot, after founder selection

The gates, 2–3 variant count, viewport/locale coverage and handover record below are **Rancana's proposed protocol**, informed by the thread; they are not attributed to Faiz as an exact checklist.

1. **Record references first.** Use only the thread and approved Rancana sources above for this handover. Every later reference row must record its exact source, inspected evidence, pattern to borrow, exclusions, Rancana adaptation and verification status. Keep candidates separate from inspected references; do not infer patterns from names, snippets or login shells. Capture the chosen page's current full-page rendering and baseline commit. Editable import is optional if a suitable tool is already available.
2. **Gate one real page.** Pilot route: **not selected**. Obtain explicit founder agreement on one existing route, locale scope, light theme, allowed content/layout changes and token subset. Proposed tokens need approval for that pilot; otherwise retain shipped values. This documentation change authorizes no pilot implementation.
3. **Create 2–3 composition variants.** Keep the same agreed content, approved asset bytes and approved token subset. Name the deliberate composition differences and include the unchanged page as baseline. Catalog cards A/B are reference recipes, not a selected page direction.
4. **Render matched comparisons.** Show baseline plus variants side by side at **320, 390 and 1440px**, recording route, locale, viewport, source commit, interaction state and deterministic motion pose. Review both ID/EN where localized, comparing each locale with its own unchanged baseline and copy. Keep full-page captures plus useful detail crops; use real page renders.
5. **Polish manually, then record a decision.** Fix findings below, rerender affected comparisons and present the concrete result. Record founder accept/amend/reject or no decision, with reasons. A recommendation remains proposed until explicitly chosen.
6. **Promote accepted patterns only.** Document anatomy, states, token dependencies and responsive rules. Handover the exact source/evidence and decision record to Muse/ChatGPT. Adoption affects only the approved pilot; further pages, Flutter mapping and release remain separate decisions.

## Render-review checklist

- **Typography:** loaded families/weights, hierarchy, ID/EN wrapping, line-height and reading size; keep unchosen button/caption recipes proposed.
- **Spacing/composition:** rhythm, card density, alignment, mobile order and unintended overflow at all three widths.
- **Artwork:** original bytes, aspect ratio, texture, silhouette, face/hands, established context and reduced-motion behavior where applicable.
- **Interaction:** focus, hover/pressed/disabled states, hit areas, links, form feedback and relevant transitions; run applicable existing checks.
- **Semantics:** foreground/background pairs and contrast in real textured contexts; preserve subject categories, selectable palettes and unrelated pages.

Dark semantic planning can remain a proposal while the light pilot is reviewed. That is neither a failed requirement nor permission to implement dark mode. Flutter acceptance still requires actual Flutter captures.
